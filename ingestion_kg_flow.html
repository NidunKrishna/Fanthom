Fathom · Ingestion detail

Ingestion → Knowledge Graph construction

Zoomed into stage 01–03 only. Two kinds of raw data come in — structured events/records and unstructured text — and take different extraction paths before merging into one knowledge graph. Structured data is mapped deterministically; unstructured text goes through a LangChain + LLM extraction step. Both converge through entity resolution before being written to the graph.

02Ingestion — two parallel paths
Structured records already carry clean IDs and typed fields, so they skip the LLM entirely. Only free text goes through extraction — cheaper, faster, and avoids letting an LLM hallucinate a relationship that a field already states exactly.
Structured path — deterministic
No LLM call. A fixed mapping table turns each record type directly into node/edge upserts.

Schema validation

Unstructured path — LLM extraction
LangChain-orchestrated. Only source of nodes/edges the LLM has to infer rather than read off a field.
2b.1
Chunking
Transcripts, descriptions, bios, comments split into ~500-token passages, each tagged with its source_id and source_type.

2b.2
LangChain LLMGraphTransformer
Each chunk sent to Gemini with an allowed node/relationship ontology, so extraction stays inside the target schema instead of free-form.

Confidence scoring
Every extracted node/edge carries the LLM's confidence; anything below threshold is flagged for review instead of auto-committed to the KG.

03Entity resolution
Canonicalize before writing
Structured entities already have IDs, so they resolve by direct match. LLM-extracted topics/entities don't — "e-bikes" and "electric bikes" must land on the same node. Candidate names are embedded and compared against existing KG node embeddings (reusing the embedding model from the RAG layer); above a similarity threshold they're aliased onto the existing node, below it they create a new one.
embed("e-bikes") · embed("electric bikes") → cosine 0.94 ≥ 0.90 threshold → alias "e-bikes" onto existing Topic node "electric bikes"
04Graph write
Streaming upsert
Interaction & search events write near-real-time, so WATCHED/LIKED/SKIPPED edges land within minutes of the action.
Batch upsert
Catalog metadata and unstructured extraction run on a nightly batch, since transcripts/descriptions rarely change after upload.
Idempotent keys
Nodes keyed by canonical ID, edges keyed by (source, target, edge_type) — reprocessing the same event never duplicates a node or edge.
Target store today is graph_ds.Graph in-memory; a persistent graph DB (Neo4j / Memgraph) would sit here unchanged once scale requires it — the mapping and extraction steps above don't depend on which store it is.
05Validation gate
Before commit
Ontology check — reject any node/edge type not in the allowed schema below. Orphan check — an edge referencing a node that doesn't exist yet is queued and retried rather than silently dropped (handles out-of-order events, e.g. a watch event arriving before its video's catalog record).
