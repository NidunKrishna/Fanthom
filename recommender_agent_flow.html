Recommender agent — detailed flow

One of the three LangChain agents. Takes a user + KG, produces a ranked, explained list of candidate videos, and hands it to the Validator agent. Internally it's an agent loop over tools, where each tool is a RecommenderAdapter implementation — the same interface already built in recommenders/ — so ranking strategies stay swappable without touching the agent's control flow.

01Trigger
Invocation
Orchestrator calls the Recommender agent for a feed request or refresh.

02Candidate generation
Ranking never runs over the whole catalog. The agent first pulls a bounded candidate pool from the KG, then ranks within it.
2-hop graph traversal
From User, out through WATCHED/LIKED videos, across shared Topic/Tag/Creator nodes, back in to other Videos.
User -[WATCHED]-> Video -[HAS_TOPIC]-> Topic <-[HAS_TOPIC]- Video (candidate)
Trending / popularity pool
Top-N videos by recent engagement, independent of this user — adds coverage the graph pool misses.
Freshness pool
Recently uploaded videos matching the user's PREFERS topics, so new content isn't starved by watch-history bias.
Seen-filter
Drops videos already in the user's WATCHED or SKIPPED edges from all three pools above.
applied last, across all pools
03Strategy selection — agent decides warm vs. cold
The agent inspects how connected the user is in the KG (edge count off their User node) and picks which adapter(s) to invoke. This decision — not the ranking math itself — is the one piece of actual agent reasoning in the loop.
Warm user
User has enough WATCHED/LIKED edges for graph signal to be meaningful (threshold, e.g. ≥ 3 interactions).

04Adapter tools — what the agent actually calls
Every strategy above is exposed to the LangChain agent as a tool with the same call shape, wrapping the RecommenderAdapter interface. Adding a new ranking strategy later means adding one more tool — the agent's loop and the Validator downstream don't change.

05Merge, diversify, truncate
Combine adapter outputs into one list
Scores from multiple invoked adapters are normalized to a common 0–1 range, then combined with adapter weights (e.g. graph 0.8 / popularity 0.2 for warm users). A diversity constraint caps how many results can share the same Creator, so one prolific creator can't fill the whole feed. The list is then truncated to the requested k.
final_score = 0.8 * norm(graph_score) + 0.2 * norm(popularity_score) cap: max 2 results per Creator truncate to k=10, best first
